# Конфигурация Avito Parser

Файл конфигурации: **`config.toml`** в корне проекта.

- Загружается модулем `load_config.py` (`tomllib`) и валидируется моделью `AvitoConfig` (`domain/config.py`).
- Все настройки лежат в секции `[avito]`.
- Вносить настройки можно двумя способами (они пишут в один файл):
  1. **GUI** (`python AvitoParser.py`) — форма Flet: загружает `config.toml` при старте и сохраняет обратно при нажатии кнопок.
  2. **Вручную** — редактирование `config.toml` текстом (нужно для CLI/сервера/Docker).
- Некоторые параметры есть в модели `AvitoConfig`, но **не выведены** в `config.toml`/GUI (используются значения по умолчанию) — они отмечены в тексте.

> ⚠️ Формат TOML: строки в `"..."`, массивы в `[...]` (без висячей запятой после последнего элемента), булевы значения — `true`/`false`, комментарии — `#`.

## 📌 Ссылки и объёмы

### `links` — мапа (ключ = ссылка, значение = объект)

Ссылки на поиск/категории Avito для мониторинга. Каждая ссылка преобразуется в мобильный API-адрес (через сервис SPFA) и проверяется отдельно.

```toml
[avito.links]
"https://www.avito.ru/...?q=игровой+пк" = {}
"https://www.avito.ru/...videokarty?q=rtx" = { min_price = 10000, max_price = 50000, white_list = ["rtx"], black_list = ["сломан"], geo = "Новосибирск", start_date = "2026-01-01", ignore_promotion = true }
```

**Поиск по ключевому слову** задаётся самой ссылкой (параметр `?q=...` в URL Avito).
**Обязательный параметр** — без ссылок парсеру нечего отслеживать.

В значении объекта можно задать (всё опционально):
- `min_price` / `max_price` — границы цены для ссылки;
- `white_list` / `black_list` — белый/чёрный списки слов для ссылки;
- `geo` — город (фильтр по региону, совпадение с `location.name`/`formattedAddress`);
- `start_date` — дата `"YYYY-MM-DD"`, с которой искать объявления (не раньше);
- `ignore_reserv` — пропускать «Зарезервировано» (по умолчанию `true`);
- `ignore_promotion` — пропускать продвигаемые (по умолчанию `false`).

Пустой объект `{}` означает «без ограничений на ссылку».

### `count` — целое число

Сколько страниц (по ~50 объявлений) брать за проход по каждой ссылке.

```toml
count = 1   # только первая страница
```

`1` — одна страница, `2` — две и т.д. В GUI-режиме ограничение — до 100 ссылок; в CLI ограничений нет.

## 🎯 Фильтры (задаются на каждую ссылку)

Все фильтры объявлений задаются **в `[avito.links]`** для каждой ссылки отдельно
(см. раздел «Ссылки и объёмы»). Глобальных `white_list`/`black_list`/`min_price`/`max_price`/
`geo`/`max_age`/`ignore_reserv`/`ignore_promotion` в `[avito]` больше нет.

| Фильтр            | Ключ в `links`             | Что делает                                                                  |
| ----------------- | -------------------------- | --------------------------------------------------------------------------- |
| Цена              | `min_price`/`max_price`    | `min_price <= priceDetailed.value <= max_price`                              |
| Чёрный список     | `black_list`               | исключить при совпадении фразы в заголовке/описании (регистронезависимо)     |
| Белый список      | `white_list`               | оставить при совпадении хотя бы одной фразы                                 |
| Город             | `geo`                      | совпадение с `location.name` / `namePrepositional` / `geo.formattedAddress` |
| Дата публикации   | `start_date`               | оставить объявления, опубликованные не раньше `"YYYY-MM-DD"`                |
| «Зарезервировано» | `ignore_reserv`            | `true` — пропускать (по умолчанию `true`)                                    |
| «Продвинуто»      | `ignore_promotion`         | `true` — пропускать (по умолчанию `false`)                                   |

### `seller_black_list` — массив строк (глобальный)

Чёрный список продавцов (по `sellerId`) — единственный глобальный фильтр. Объявления этих продавцов пропускаются.

```toml
seller_black_list = ["sales-user-12345"]
```

> Порядок применения фильтров (`filters/ads_filter.py`): уже просмотренные → цена → чёрный список ключевых слов → белый список → город → продавцы → дата публикации → «Зарезервировано» → «Продвинуто».

## ⏱ Паузы и повторы

### `pause_general` — число ≥ 0 (секунды)

**Общий перерыв между раундами всех поисковых ссылок.** Раунд заканчивается,
когда каждая актуальная ссылка завершила обход своих страниц (включая неуспешные
попытки). Быстрая ссылка не начинает повторный обход, пока остальные не закончили.
От этого момента отсчитывается `pause_general`; во время перерыва очередь
обрабатывает просроченные карточки объявлений. Затем начинается следующий раунд.

```toml
[avito]
pause_general = 300   # 5 минут общего перерыва после всех поисковых ссылок
```

Это существующий параметр с новым общим действием; дополнительного поля для паузы
одной ссылки нет. Значение `0` отключает перерыв и фоновые обновления между раундами.
Настройка читается при запуске. Интервал готовности отдельной карточки к обновлению
по-прежнему задаёт `ad_refresh_interval`.

Изменение фильтров отменяет старый обход и сразу запускает новый для этой ссылки
с первой страницы, в том числе во время перерыва. Новая ссылка также запускается
сразу; удаление останавливает её обход. Эти действия не переносят установленный
срок окончания общего перерыва. Уже выполняющийся запрос другой ссылки завершается
перед запросами изменённой ссылки: сетевые вызовы остаются последовательными.

### `min_delay` / `max_delay` — числа (секунды)

Границы **случайной задержки между запросами к Avito**. Все запросы к Avito (поисковая выдача, страницы объявлений) из всех ссылок идут через общую очередь: между двумя соседними запросами выдерживается случайная пауза из диапазона `[min_delay, max_delay]`. Пауза запускается только после того, как предыдущий запрос полностью обработался.

```toml
min_delay = 1.0
max_delay = 3.0
```

### `max_count_of_retry` — целое число

Максимум обычных HTTP-попыток запроса при ошибке. Ожидание cookies SPFA ограничено
отдельным окном `spfa_unblock_timeout` и не посылает запросы к Avito. После завершения
ожидания допускается одна дополнительная попытка с новым набором cookies, если
обычный лимит уже исчерпан.

```toml
max_count_of_retry = 5
```

### `retry_delay` — целое число (секунды)

Пауза между обычными повторными попытками при ошибке запроса. Пока SPFA выполняет
разблокировку, вместо неё используется `spfa_unblock_check_interval`.

### `timeout` — целое число (секунды)

Таймаут HTTP-запроса.

```toml
timeout = 30
```

### `block_threshold` — целое число

Сколько блокировок (403/429/439) подряд нужно, чтобы запустить «обработку бана»: смена IP (если мобильный прокси) + обновление/покупка cookies (SPFA).

```toml
block_threshold = 3
```

Проверка одной ссылки использует те же клиенты и параметры, что и парсер:

```sh
python scripts/retrieve_ad_links.py "https://www.avito.ru/..." --mobile-proxy --no-restart --save-html ad-mobile.html --save-json ad-mobile.json
```

При `camoufox.use = true` запрос выполняет Camoufox, иначе HTTP-клиент с
cookies из настроек. Применяются `max_count_of_retry`, `retry_delay`,
`block_threshold` и параметры `ip_rotation_*`. После успешной смены IP
HTTP-клиент обновляет cookies и сессию; Camoufox перезапускает браузер.
После исчерпания попыток скрипт возвращает код 1 и сохраняет последний
полученный HTML. Таймаут берётся из `timeout`; `--timeout` явно переопределяет его.

### `retry_on_failure` / `retry_on_failure_delay` — устарели

Эти параметры больше **не используются**: неудачный обход ссылки повторяется
в следующем общем раунде после перерыва `pause_general`.
Поля оставлены в конфиге для обратной совместимости, но на работу не влияют.

## 🛡 Прокси и обход блокировок

### Свой мобильный прокси (`[avito.own_mobile_proxy]`)

tinyproxy, запущенный на телефоне (Termux), — трафик идёт через мобильную сеть.
Запускается через выбранный transport (SSH или ADB) через `nohup ... &` (без tmux) и живёт независимо от SSH-сессии.
При запуске и перезапуске через SSH выполняется `scripts/fix_interfaces_via_ssh.sh` (маршрутизация Termux
через мобильный интерфейс + обновление `Bind` в `tinyproxy.conf`), причём в порядке
**стоп tinyproxy → fix_interfaces_via_ssh.sh → старт tinyproxy**.
При ADB выполняются остановка, запуск через nohup и проверка процесса; настройки
сети и tinyproxy.conf сохраняются. TCP-трафик **всегда** пробрасывается через ADB,
включая управление телефоном через SSH. `adb_forward = [port1, port2]` задаёт
порт ADB на сервере и порт tinyproxy на телефоне. `server = "host:port"` задаёт
полный адрес подключения к прокси. Если в server указан только host, берётся port1;
пустой server означает `127.0.0.1:port1`. `ssh.host` относится только к телефону.
Тот же адрес (с `login:password@`, если задана авторизация) уходит в SPFA в поле `proxy` тела запроса, а сам
запрос к SPFA выполняется через `[avito.messengers].proxy_notifier`.

Запуск/остановка:
- только прокси: `python scripts/run_proxy.py [--verify|--stop]`;
- вместе с сервисами: `python run.py`;
- всё остановить: `python scripts/stop.py` (без `--keep-proxy`).

```toml
[avito.own_mobile_proxy]
use = true          # true — трафик через свой мобильный прокси
transport = "adb"   # adb или ssh — управление телефоном; TCP всегда через ADB
adb_forward = [15556, 5556] # [TCP-порт ADB на сервере, Port из tinyproxy.conf]
rotate_ip = true    # смена IP через выбранный транспорт при блокировках
adb_serial = ""     # серийник устройства для adb (пусто — adb без -s)
login = ""          # опционально: логин HTTP (tinyproxy BasicAuth)
password = ""       # опционально: пароль HTTP (tinyproxy BasicAuth)
server = ""         # host или host:port; без порта — adb_forward[0], пусто = localhost

[avito.own_mobile_proxy.ssh]
host = "192.168.1.50"   # IP-адрес телефона (только для SSH)
port = 8022             # порт SSH (Termux sshd)
user = "u0_a123"        # пользователь SSH (whoami в Termux)
password = "***"        # пароль SSH
```

Для SSH нужны `paramiko`, Termux sshd и настройки секции ssh.
Для TCP-проброса при любом transport нужны adb в PATH и подключённый телефон.
Для ADB нужны adb в PATH, доступное устройство (adb_serial либо единственное
подключённое устройство) и работающий `run-as com.termux` для запуска tinyproxy,
проверки статуса и чтения логов. Эти команды выполняются без su и поиска UID:

```sh
run-as com.termux files/usr/bin/env -C /data/user/0/com.termux/files/home \
  PATH=/data/data/com.termux/files/usr/bin \
  LD_PRELOAD=/data/data/com.termux/files/usr/lib/libtermux-exec.so \
  HOME=/data/user/0/com.termux/files/home \
  /data/data/com.termux/files/usr/bin/bash -lc 'COMMAND'
```

Рабочий каталог и переменные окружения задаются через `env`. Смена IP выполняется
через выбранный транспорт. При SSH перед запуском/перезапуском выполняется
scripts/fix_interfaces_via_ssh.sh (нужен root/su на телефоне).
При ADB готовая конфигурация Termux используется без настройки интерфейсов.
Для режима полёта через ADB сохраняются отдельные root-команды
`su -c 'cmd connectivity airplane-mode enable/disable'`.

`python scripts/run_proxy.py --stop` останавливает прокси и при `use = false`:
завершает процесс чтения логов и его дочерний ADB-клиент, монитор проброса,
удаляет принадлежащий проекту `adb forward`, затем завершает удалённые `tail`
и tinyproxy. Для tinyproxy сначала отправляется SIGTERM и проверяется статус
до 5 секунд; если процесс ещё работает — SIGKILL и проверка до 2,5 секунд.
Перезапуск также ждёт завершения старого tinyproxy перед запуском нового.
Остановка через `pkill -f` (при необходимости `pkill -9 -f`) и проверка
статуса через `pgrep -f` используют один шаблон полного пути
`/data/data/com.termux/files/usr/bin/tinyproxy` в начале командной строки.
При недоступном телефоне локальная очистка всё равно выполняется.
Если удалить проброс не удалось, его состояние сохраняется для повторной
остановки; команды остановки возвращают ненулевой код при ошибке.
Запуск и остановка чтения логов защищены файловой блокировкой: одновременный
старт парсера и веб-сервера не создаёт второй неучтённый процесс.

Проброс выполняется напрямую: `adb -s SERIAL forward tcp:port1 tcp:port2`.
TCP обслуживает сам ADB-сервер, дополнительного TCP-приёмника в проекте нет.
Интерфейс проброшенного порта зависит от уже запущенного ADB-сервера:
обычно localhost, а при его запуске с `-a` — все интерфейсы.
Источник: [реализация TCP listener в ADB](https://android.googlesource.com/platform/packages/modules/adb/+/f4965b77c694689c08855076eaf983c8e88646f9/socket_spec.cpp).

Проброс создаётся при запуске, в том числе если tinyproxy уже работает,
восстанавливается после смены IP и обновляется монитором
`scripts/watch_tinyproxy_forward.py` каждые 5 секунд. Монитор не открывает сокеты
и не передаёт трафик; при отключении устройства повторяет настройку после его возвращения.
Ошибка его создания делает запуск неуспешным; ошибка при смене IP передаётся
механизму повторных попыток. При остановке прокси монитор завершается, а его ADB-forward удаляется.
Состояние процесса — `logs/tinyproxy_forward.json`, диагностика —
`logs/tinyproxy_forward.log`, команды и ответы ADB — `logs/adb.log`.
Для внешнего доступа используйте nginx stream: клиент → nginx →
127.0.0.1:port1 → ADB → телефон:port2. Например, `adb_forward = [15556, 5556]`,
`server = "127.0.0.1"` для локального парсера и внешний порт nginx 5556.
В конфигурации nginx на верхнем уровне (рядом с http):

```nginx
stream {
    server {
        listen 5556;
        allow 198.51.100.10; # замените на IP клиента
        deny all;
        proxy_connect_timeout 5s;
        proxy_timeout 120s;
        proxy_pass 127.0.0.1:15556;
    }
}
```

TLS и ограничения внешнего доступа настраиваются в nginx. Для HTTPS-прокси
добавьте `ssl` в listen и сертификаты. Текущий парсер использует обычный HTTP-прокси
на локальном порту ADB. Публикация через nginx не меняет адрес, возвращаемый
get_spfa_proxy_string: внешний сервис требует доступного извне адреса и согласованного порта.
Например, `server = "90.189.153.8:5556"` направляет HTTP-клиент, браузер и SPFA
на внешний HTTP-порт nginx 5556 при `adb_forward = [15556, 5556]`.
Порт в server не изменяет настройки ADB-проброса. IPv6 с портом указывается
в квадратных скобках: `server = "[::1]:5556"`. Поддерживается HTTP-прокси;
TLS к самому прокси пока не настраивается через server.
Источник: [nginx stream proxy_pass](https://nginx.org/en/docs/stream/ngx_stream_proxy_module.html#proxy_pass).
Поле `port` устарело; массив `adb_forward` имеет приоритет. Старые bool-значения
и конфиги без массива читаются как `[port, port]` и больше не отключают проброс.

Логи tinyproxy пишутся на телефоне: вывод nohup перенаправляется в файл;
только при SSH в tinyproxy.conf выставляются LogFile и Syslog Off. Логи
**стримятся на хост парсера** в `logs/tinyproxy.log` — фоновым процессом
`scripts/follow_tinyproxy_log.py` (pid в `logs/tinyproxy_follow.pid`, диагностика в
`logs/tinyproxy_follow.log`). Стрим стартует вместе с прокси и останавливается
вместе с ним (`run_proxy.py --stop`, `scripts/stop.py`), переподключается при обрыве
SSH/ADB. Путь лога на телефоне по умолчанию — `/data/data/com.termux/files/home/tinyproxy.log`,
меняется флагом `python scripts/run_proxy.py --device-log <путь>`.

### Внешний мобильный прокси (`[avito.external_mobile_proxy]`)

Платный мобильный прокси (например, mobileproxy.rent). Если `proxy_string` задан
вместе с `change_urls` — прокси умеет менять IP; без `change_urls` — это обычный
статический (серверный) прокси.

```toml
[avito.external_mobile_proxy]
proxy_string = "login:pass@mproxy.site:11139"
change_urls = [
    "https://changeip.mobileproxy.space/?proxy_key=***",
    "https://aproxy.site/?proxy_key=***",
]
```

- Формат `proxy_string`: `username:password@host:port`.
- `change_urls` — список ссылок смены IP.
- При блокировке парсер перебирает `change_urls` **по порядку**, пока запрос не
  выполнится успешно (200 и непустой `new_ip`).
- Только **HTTP(S)** — SOCKS не поддерживается без правки кода.

Приоритет: если `[avito.own_mobile_proxy].use = true`, используется свой мобильный
прокси, а внешний игнорируется.

### `use_bypass_api` — булево

`true` — использовать сторонний сервис cookies **SPFA (spfa.pro)**: покупка и разблокировка cookies при блокировках.

```toml
use_bypass_api = false
```

### `cookies_api_key` — строка

API-ключ сервиса SPFA. Нужен при `use_bypass_api = true` (и для парсинга телефонов).

```toml
cookies_api_key = ""
```

### `own_cookies` — булево

`true` — свои cookies получаются **напрямую с Avito** по алгоритму `scripts/fetch_cookies.py`:
curl_cffi (`chrome131_android`) делает `GET https://www.avito.ru/` через мобильный прокси и собирает
`Set-Cookie`. При блокировке вместо разблокировки/покупки куки просто перевыпускаются тем же GET.

```toml
own_cookies = false
```

- Имеет приоритет над `use_bypass_api` (в фабрике проверяется первым).
- Куки сохраняются в `storage/own_cookies.json`.
- Требует, чтобы был задан прокси ([avito.own_mobile_proxy] или [avito.external_mobile_proxy]) —
  запрос к Avito идёт через него.
- `own_cookies = false` ничего не меняет: работает прежняя логика (`use_bypass_api` → SPFA).

### `purchase_cooldown` — целое число (секунды)

Минимальный интервал между повторными покупками cookies через SPFA (защита баланса).
По умолчанию `600` (10 минут).

Разблокировка завершается только после ответа SPFA `success: true` с актуальными
`results.cookies` и совпадающим ID. Набор заменяется целиком, сохраняется на диск и
передаётся в новую HTTP-сессию. Ответ Avito сам по себе не завершает ожидание SPFA.

### `spfa_unblock_timeout` / `spfa_unblock_check_interval` — секунды

```toml
[avito]
spfa_unblock_timeout = 300
spfa_unblock_check_interval = 30
```

Запрос `/unblock/` синхронно ожидает ответ сервиса с таймаутом
`spfa_unblock_timeout`. HTTP 200 и 202 проверяются по JSON: нужны `success: true`,
совпадающий `results.id` и непустой `results.cookies`. Старые cookies заменяются
полученным набором, затем пересоздаётся HTTP-сессия. Покупка `/cookies/mobile/`
также синхронна и использует этот таймаут; запросы Avito продолжаются после получения
и проверки cookies, user-agent и fingerprint.

HTTP 202 с этими полями завершает ожидание так же, как HTTP 200.
Если SPFA отвечает 409 или не возвращает подтверждённый набор в 200/202, IP сохраняется,
Avito остаётся на паузе. Через `spfa_unblock_check_interval` секунд повторяется
запрос **к SPFA `/unblock/`**, а не к Avito. Отдельного endpoint статуса в используемой
[документации SPFA](https://spfa.pro/api/docs/) нет; повторный POST вызывает тот же
метод восстановления. HTTP 404/410 от SPFA приводит к покупке нового набора.

Ошибки и промежуточные ответы не продлевают текущее окно. По его истечении задание
завершается `UnblockTimeoutError`. Следующее задание начинает новое окно ожидания
SPFA с тем же IP; до получения cookies запросы Avito остаются запрещены.
При ошибке обновления карточки старые данные и `last_attempt` сохраняются.
Отмена задания не снимает ожидание: следующее продолжает восстановление.

Поиск и обновления карточек занимают общий слот очереди на весь процесс восстановления.
Загрузка фото с CDN также ждёт SPFA; уже начатая загрузка завершается до запроса
разблокировки. Отправка ранее загруженных фото и текстов в мессенджеры может продолжаться.
Это согласование действует внутри одного процесса парсера, не между отдельными запусками CLI.

Оба значения должны быть конечными числами больше нуля; интервал должен быть
меньше срока ожидания. При отсутствии полей действуют значения `300` и `30`.
Настройки относятся к SPFA; Camoufox со своими cookies использует обычные повторы.

### `parse_phone` — булево

Парсить телефон продавца (через SPFA `/api/phone/`).


### `detached_mode` — булево

Как `run.py` запускает локальные процессы (API, web, парсер):

- `false` (по умолчанию) — в tmux-сессиях `api`, `web` (`--dev`), `parser`;

## Извлечение ссылок карточек из выдачи

```bash
python3 scripts/retrieve_ad_links.py 'https://www.avito.ru/novosibirsk/tovary_dlya_kompyutera/komplektuyuschie/protsessory/amd-ASgBAgICA0TGB~pm7gniZ~LNE4q85hE?cd=1&q=ryzen+5+5500x3d' \
  --extract-links --mobile-proxy --no-restart \
  --pages 1 --save-links links.txt --save-json links.json
```

Исходная поисковая ссылка преобразуется существующим `AvitoUrlConverter` через SPFA
(либо берётся из кэша). Каталог запрашивается клиентом программы с cookies, прокси,
лимитами повторов и сменой IP из конфигурации. При `camoufox.use=true` используется
Camoufox с его браузерными cookies, иначе HTTP-клиент с выбранным провайдером cookies.

`--pages` задаёт максимальное число страниц начиная с первой (по умолчанию 1).
Пустая страница завершает обход. Между страницами применяется `min_delay`/`max_delay`.
Повторные ID исключаются. Карточки не запрашиваются: из ID строятся ссылки
`https://m.avito.ru/api/1/card/items/{id}`. Они печатаются и сохраняются в `links.txt`.
`links.json` содержит массив объектов `id`, `title`, `url` (обычный URL с параметрами
из `urlPath`) и `api_url`. Фильтры подписок и история просмотренных здесь не применяются.
Если запрос или разбор каталога завершился ошибкой, код выхода — 1; итоговые файлы
создаются только после успешного сбора всех запрошенных страниц (или пустой страницы).
Ранее созданные файлы при ошибке не обновляются.

## Проверка мобильной API-карточки

Передайте `api_url` из `retrieve_ad_links.py`:

```bash
python3 scripts/test_ad_link.py \
  'https://m.avito.ru/api/1/card/items/8258446852' \
  --mobile-proxy --no-restart \
  --save-json ad.json --save-response ad-response.txt
```

Скрипт выводит и сохраняет полный JSON, включая поля, которые основной парсер
пока не использует. `--save-response` сохраняет тело последнего ответа и при
ошибке (например, HTML блокировки). Код выхода 1 означает ошибку запроса, разбора
JSON или явную ошибку API; при успехе — 0. Старый JSON-файл не обновляется,
если новый ответ не удалось получить или разобрать.

Используется та же фабрика клиента, что у `retrieve_ad_links.py`: прокси,
провайдер cookies, `timeout`, `max_count_of_retry`, `retry_delay`, `block_threshold`
и параметры повторов смены IP берутся из `config.toml`. Дополнительного цикла
повторов в скрипте нет. При `camoufox.use=true` используется браузерный клиент
и его cookies. Для HTTP-клиента задаются Accept JSON и мобильный Referer;
User-Agent и TLS fingerprint не подменяются жёстко заданным Chrome/Android.

Без `--no-restart` собственный tinyproxy перезапускается перед запросом;
с этим флагом проверяется его работа (при необходимости запускается).
`--no-proxy` пропускает только управление tinyproxy, но сохраняет настроенный
прокси для запросов. `--config` выбирает конфигурацию, `--timeout` позволяет
явно переопределить её таймаут. Скрипт не отправляет уведомления и не записывает
объявление в базу парсера.

## Автоматическое обновление сохранённых объявлений

В `[avito]`:

```toml
ad_refresh_interval = 3600  # секунды; 0 отключает фоновые проверки
```

По умолчанию — один час. Настройка читается при запуске парсера.
Для каждого ID база хранит в `last_attempt` время последнего успешного обновления. Первая
проверка назначается через этот интервал после сохранения объявления; для старой
базы срок считается от `scanned_at`. Одинаковый ID в нескольких подписках
проверяется одним запросом, результат обновляет все его строки. Повторное обнаружение
в выдаче и перезапуск программы не сбрасывают срок. Просроченные карточки ждут
в базе и выбираются от самых давно проверенных.

Запросы проходят через общую последовательную очередь:

1. Раунд охватывает все поисковые ссылки: все их страницы и дополнительные
   запросы, включая получение полных описаний. Обновления ждут конца всего раунда.
2. После завершения раунда начинается общий перерыв `pause_general`. В это окно
   просроченные карточки выбираются из базы и по одной добавляются в очередь:
   `https://m.avito.ru/api/1/card/items/{id}`. Индивидуальные сроки не сбрасываются.
3. По истечении перерыва новый раунд получает приоритет перед ожидающим обновлением.
   Уже начатый запрос, включая повторы и восстановление сессии, завершается в текущем
   слоте очереди. Остальные карточки ждут следующего перерыва. Обычные уведомления
   отправляются отдельным потоком и не задерживают раунды.

Общие `min_delay`/`max_delay`, HTTP-клиент (или Camoufox), cookies, прокси, лимиты
блокировок и смены IP применяются и к карточкам. Исчерпание попыток смены IP
останавливает парсер. При ошибке или отмене данные и `last_attempt` не изменяются.
Карточка остаётся просроченной; после ошибки фоновый обработчик выдерживает паузу
3 секунды и снова выбирает самое старое объявление через общую очередь с обычными
задержками. Постоянно ошибающийся самый старый ID может задерживать остальные
обновления; поисковые раунды сохраняют приоритет. Новый срок `ad_refresh_interval`
отсчитывается только после успешного обновления.
Интервал определяет момент готовности к проверке, а не гарантированный срок:
если все просроченные карточки не помещаются в перерыв, оставшиеся ждут следующего.
Перерыв должен быть достаточно длинным с учётом `min_delay`/`max_delay` и повторов;
при `pause_general = 0` окна для обновлений нет.

Обновляются доступные в ответе название, полное описание, цена, ссылка, дата,
город и адрес, доставка, продавец, рейтинг и отзывы, фото, координаты, категория,
наличие видео и бронь. Отсутствующие или неоднозначные поля не затираются.
При успешном обновлении `refreshed_at` получает текущее время UTC, а `scanned_at`
сохраняет время первоначального парсинга. Поля объявления, `refreshed_at` и
`last_attempt` записываются одной транзакцией: ошибка записи откатывает все изменения.
В веб-таблице показаны `scanned_at` в колонке «Время парсинга» и `refreshed_at` в колонке
«Обновлено» (с сортировкой по ней); если успешных обновлений ещё не было, в «Обновлено»
показано «—». Ранее созданные Excel-файлы не переписываются.

Удаление из базы и очистка неотправленных уведомлений происходят только при явном
статусе снятого/удалённого объявления в JSON. Сам по себе HTTP 404/410, HTML,
блокировка или ошибка сети не служат основанием для удаления.

UI показывает метку «Забронировано» и колонки «Время парсинга» и «Обновлено», перечитывая базу каждые
10 секунд на открытой странице объявлений. Бронь обновляется также из `isReserved`
каталога, в том числе для ранее сохранённых объявлений, которые не прошли фильтры
текущего обхода. Объединённый признак `is_reserved_or_out_of_stock=true` не считается
доказательством брони; значение false позволяет снять старую отметку.

## Диагностика обходов и уведомлений

Парсер создаёт четыре файла в `logs/`:

| Файл | Содержимое |
| --- | --- |
| `app.log` | Общий лог со всеми сообщениями приложения |
| `scanning.log` | Начало и завершение раундов, общий перерыв, обход страниц, фильтры, сохранение и обновление карточек |
| `notifications.log` | Очередь уведомлений, начало и результат доставки, повторы, запросы мессенджеров и скачивание фотографий |
| `blocking.log` | HTTP/Camoufox-запросы и ошибки, блокировки, cookies/SPFA, попытки смены IP, управление прокси и команды ADB |

Дополнительно `events.jsonl` содержит единый поток JSON-событий для Alloy/Loki.
Обычные файлы продолжают записываться. [Запуск Grafana + Loki + Alloy](MONITORING.md)
настраивается отдельно, через `monitoring/.env`, без изменения `config.toml`.

Сообщения отдельных журналов также остаются в `app.log`. Для каждого файла действуют
ротация по 5 МБ и хранение 5 дней; маскировка секретов применяется ко всем журналам.
Отдельные существующие `adb.log` и `tinyproxy.log` сохраняются. Системные сообщения,
не относящиеся к этим трём алгоритмам, остаются в общем журнале.
Процесс смены IP передаёт свои сообщения родительскому процессу: они также
попадают в `blocking.log` и `app.log`, сохраняя имя исходного модуля в тексте.

Итог обхода различает полностью успешный, частично успешный и неуспешный результат.
В нём указаны число обработанных страниц и номера страниц с ошибками запроса или
валидации. Корректный пустой каталог завершает обход успешно; некорректный JSON
каталога не считается успешно обработанной страницей.

Токены Telegram в сообщениях Loguru и текстах исключений маскируются, в том числе
в URL `/bot…/sendMessage`. Для исключений с секретами подробный traceback с локальными
переменными заменяется безопасным описанием цепочки ошибок. Уже существующие
лог-файлы автоматически не переписываются.

Ошибки HTTP уведомлений теперь содержат `API description`, если API вернул это
поле в JSON. Полное тело ответа, параметры запроса и заголовки не логируются.
Строки `[notify photo]` показывают домен изображения, маршрут (без авторизации),
версии Requests/urllib3/OpenSSL и класс ошибки. Скачивание использует прокси Avito
(`avito_proxy` в логе), без него — прямое соединение (`direct`). Переменные окружения
прокси для скачивания фото не учитываются, в том числе при редиректах. Проверка TLS включена.

Если JSON карточки не распознан, в `scanning.log` и общем логе сохраняется
`JSON structure`: известные имена полей, типы и размеры контейнеров. Значения
(включая тексты, ID из ответа, cookies и URL) не сохраняются; неизвестные ключи
заменяются на `<field_N>`. Схема ограничена 100 узлами, пятью уровнями вложенности,
20 полями объекта и тремя образцами элементов массива. Если ответ не является JSON,
пишется `invalid_json` без тела ответа.
