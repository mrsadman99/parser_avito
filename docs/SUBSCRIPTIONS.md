# Результаты по подпискам и доставка уведомлений

Каждая запись ссылки в веб-интерфейсе имеет независимые фильтры и историю.
Одинаковые URL у разных пользователей или в нескольких записях одного
пользователя больше не заменяют настройки друг друга. Ссылки из TOML также
обрабатываются независимо. При изменении URL веб-ссылки начинается новая история;
изменение фильтров сохраняет уже найденные результаты.

Изменение фильтров через веб прерывает текущий обход и сразу запускает новый
с первой страницы без ожидания `pause_general`. Удаление ссылки завершает её
поток. У каждой записи есть версия `revision`, которая повышается при сохранении
настроек, включая изменения администратором. Даже быстрое изменение фильтров
с последующим возвратом к прежним значениям отменяет старый обход.

Во время пауз, ожидания HTTP-блокировки, задержек перед запросами и повторными
попытками состояние проверяется каждые 100 мс. Перед обработкой ответа и
сохранением страницы выполняется дополнительная проверка. Уже выполняющийся
синхронный сетевой вызов не обрывается: после его завершения или таймаута
устаревший ответ отбрасывается. Новый обход соблюдает обычные ограничения
частоты запросов. Ошибка чтения веб-базы сама по себе не считается удалением.

Результаты и уведомления уже принятых страниц сохраняются. Excel теперь также
пополняется после каждой страницы, чтобы отмена следующей страницы не приводила
к потере уже обработанных объявлений в файле. Начатое сохранение страницы
завершается перед выходом из старого обхода.

Веб-интерфейс получает результаты через `GET /api/ads?link_id=123`. Сервер
проверяет владельца; администратор может читать любую подписку. Старый запрос
`GET /api/ads?url=...` для обычного пользователя возвращает только результаты
его подписок. Для администратора он возвращает всю историю этого URL, включая
старые записи и результаты из TOML.

## Результат смены IP

После достижения `block_threshold` клиент проверяет результат
`proxy.rotate_with_retries()`. При `False`, исключении или таймауте очередной
попытки смена IP повторяется. Настройки в секции `[avito]`:

```toml
ip_rotation_attempts = 3
ip_rotation_timeout = 90
ip_rotation_retry_delay = 5
```

`ip_rotation_attempts` — общее число попыток, включая первую.
`ip_rotation_timeout` — время одной полной попытки в секундах, включая запуск
процесса, ADB, ожидания режима полёта и SSH. Зависшая попытка выполняется
в отдельном процессе и принудительно завершается по таймауту. Между попытками
действует `ip_rotation_retry_delay`; после последней попытки паузы нет.
Для телефона только фиксированные ожидания режима полёта занимают 17 секунд,
поэтому таймаут должен оставлять время и на команды ADB/SSH.

У внешнего мобильного прокси одна попытка перебирает `change_urls` по одному
разу до первого успешного ответа. Вложенных дополнительных повторов нет.

Если все попытки неудачны, возникает `ProxyRotationError`: прекращаются все
обходы и поток уведомлений, процесс парсера завершается с кодом 1. API и фронтенд,
запущенные отдельными процессами через `run.py`, продолжают работать. В GUI
фатальная ошибка также завершает процесс приложения. Cookies не перевыпускаются,
HTTP-сессия и Camoufox не пересоздаются, счётчик блокировок не сбрасывается.
Отключённая смена IP и статический прокси также приводят к завершению после
исчерпания попыток.

Изменение или удаление подписки отменяет её смену IP и ожидание между попытками;
это не считается фатальной ошибкой парсера. Новые параметры также доступны в GUI
и сохраняются при изменении остальных настроек. Изменения TOML требуют перезапуска.

При `True` HTTP-клиент сбрасывает кэш cookies, получает cookies для нового IP
и пересоздаёт сессию; Camoufox перезапускает браузер. Затем продолжаются оставшиеся
попытки запроса. Cookies, полученные непосредственно в ответе Avito, по-прежнему
обрабатываются обычным методом `update()` до проверки порога блокировок.

## Обновление существующей базы

При первом открытии старой непустой `database.db` создаётся резервная копия
`database.db.before-subscriptions-<timestamp>.bak`. Затем автоматически добавляются
ключ подписки, уникальный индекс и очередь уведомлений. Дубли с одинаковыми
подпиской, ID объявления и ценой объединяются с сохранением последней записи.
Разные цены остаются отдельными событиями. Повторный запуск миграции безопасен.

У старых результатов нет достоверного владельца и набора применённых фильтров.
Поэтому они остаются в истории URL, доступной администратору, и не раздаются
пользователям автоматически. Веб-подписки наполнятся при следующем обходе;
уведомления для этих подписок могут прийти повторно после обновления.
Скрипт `scripts/migrate_ads.py` назначает старым записям URL, но не владельца.

Обновление объявления через `scripts/refresh_ads.py` по-прежнему меняет его
сохранённые цены; совпавшие версии объединяются внутри каждой подписки.

## Уведомления

Объявление и задания для получателей сохраняются в SQLite одной транзакцией.
Отдельный поток отправляет задания из `notification_outbox`. Временные ошибки
(сеть, HTTP 408/425/429/5xx) повторяются через 60 секунд, в том числе после
перезапуска и исчезновения объявления из выдачи. Максимум — 10 циклов доставки
для одного задания (`NOTIFICATION_MAX_ATTEMPTS` в `db_service.py`); внутри цикла
HTTP-транспорт сохраняет свои короткие повторы. Постоянные HTTP 4xx, кроме
408/425/429, и некорректный сохранённый JSON прекращают автоматические повторы сразу.
Успешная отправка отмечается отдельно для каждого получателя. Удалённые из
конфигурации получатели не обслуживаются; их задания остаются до возвращения
получателя в конфигурацию. Смена токена того же Telegram-бота или VK-токена
не сбрасывает очередь.

Задание резервируется на 10 минут, чтобы два процесса не отправляли его
одновременно. Счётчик `attempts` увеличивается при резервировании и сохраняется
между перезапусками. После аварийного завершения незавершённое задание снова
становится доступным, если лимит ещё не исчерпан. Если мессенджер принял сообщение, но процесс завершился до фиксации
успеха в SQLite, возможна повторная отправка. Гарантии ровно одной доставки нет.
Настройки получателей остаются общими для парсера, как и раньше.

После постоянной ошибки или исчерпания лимита строка сохраняется с `failed = 1`,
`sent = 0` и причиной в `last_error`; она не выдаётся из очереди и не считается
доставленной. Миграция добавляет эти поля автоматически. Старые ожидающие задания
получают `attempts = 0`, `failed = 0` и при следующей попытке форматируются текущим
кодом заново из сохранённого объявления.

Посмотреть остановленные задания можно запросом к базе парсера:

```sql
SELECT id, ad_id, attempts, last_error
FROM notification_outbox WHERE failed = 1 AND sent = 0;
```

После устранения причины конкретное задание можно вернуть в очередь вручную
(замени `123` на его ID):

```sql
UPDATE notification_outbox
SET failed = 0, attempts = 0, retry_at = 0, last_error = NULL
WHERE id = 123 AND sent = 0 AND failed = 1;
```

Новому провайдеру уведомлений рекомендуется задавать стабильный `delivery_key`,
различающий его получателей. Секретный токен не должен быть частью этого ключа.

## Проверки

```bash
python3 -B -m unittest discover -s tests -v
cd web-server
npm run build
```

Регрессионные тесты работают с временными базами и подменённой сетью.
`python run.py` теперь собирает фронтенд при каждом production-запуске,
даже если `web-server/dist` уже существует.

### Управление телефоном через ADB или SSH

В `[avito.own_mobile_proxy]` настройка `transport = "adb"` либо `transport = "ssh"`
выбирает транспорт для всех команд (включая scripts/stop.py и scripts/airplane_mode.py): запуска, остановки (включая SIGKILL), статуса,
логов, смены IP и перезапуска tinyproxy. Автоматического перехода на другой
транспорт нет. В рабочем config.toml выбран ADB; по умолчанию используется SSH.
Настройка доступна в GUI. Старый ключ restart_via читается как transport,
если transport не задан. После изменения перезапустите программу и стрим логов.

ADB требует доступного устройства, установленного Termux (com.termux),
tinyproxy, bash, coreutils, procps и работающего run-as com.termux.
Команды tinyproxy, статуса и логов выполняются без su и определения UID:

```sh
run-as com.termux files/usr/bin/env -C /data/user/0/com.termux/files/home \
  PATH=/data/data/com.termux/files/usr/bin \
  LD_PRELOAD=/data/data/com.termux/files/usr/lib/libtermux-exec.so \
  HOME=/data/user/0/com.termux/files/home \
  /data/data/com.termux/files/usr/bin/bash -lc 'COMMAND'
```

`env` задаёт рабочий каталог и переменные PATH, LD_PRELOAD, HOME перед запуском
login shell. Экспорты окружения SSH в ADB-команды не подставляются.
Строка COMMAND передаётся одним аргументом с корректным shell quoting.
Подключение предварительно проверяется командой `true` в том же shell.
Если Android запрещает run-as (например, package not debuggable), ошибка
попадает в диагностику; повышения прав через su для команд Termux нет.
[Проверки run-as в Android](https://android.googlesource.com/platform/system/core.git/+/refs/heads/master/run-as/run-as.cpp).
При transport=adb SSH-соединения не открываются. Сетевые интерфейсы, Bind,
LogFile и Syslog не изменяются: используется готовый tinyproxy.conf в Termux.
При SSH перед запуском выполняется scripts/fix_interfaces_via_ssh.sh
и настраиваются LogFile/Syslog. server задаёт host или полный адрес host:port
для подключения к HTTP-прокси. Порт из server имеет приоритет над adb_forward[0];
без порта используется adb_forward[0], пустой server означает localhost.

SSH требует настроенного Termux sshd и секции ssh. TCP-проброс всегда использует ADB,
даже при transport=ssh: adb_forward=[порт сервера, порт tinyproxy].
Команда: adb -s SERIAL forward tcp:port1 tcp:port2. TCP обрабатывает сам ADB-сервер.
При обычном запуске ADB без -a порт слушает localhost; nginx stream может
подключаться к нему напрямую и публиковать свой внешний порт с TLS и ACL.
Переключение режима полёта требует root и команды Android
cmd connectivity airplane-mode enable/disable. Оба переключения выполняются
фоновым заданием на телефоне, чтобы выключение режима полёта продолжилось при
обрыве SSH. После ожидания программа переподключается и проверяет результат.

Ошибки смены IP и перезапуска передаются общему механизму ip_rotation_attempts,
ip_rotation_timeout и ip_rotation_retry_delay. Проверка процесса tinyproxy
не заменяет проверку доступности HTTP-прокси.

### Журнал ADB

Все вызовы ADB из управления прокси и scripts/airplane_mode.py автоматически
пишутся в logs/adb.log. Формат — JSON Lines: одна запись JSON на строку.
Журнал создаётся независимо от парсера и logs/app.log, включая отдельный запуск
scripts/run_proxy.py. У каждой команды свой request_id; также сохраняются время
UTC и PID процесса на компьютере.

Событие start содержит полный список аргументов команды и timeout. finish
содержит длительность, returncode и полный stdout/stderr, даже если код равен 0.
При timeout сохраняется полученный до таймаута вывод. error содержит тип и текст
исключения (например, отсутствие adb в PATH или отказ доступа).

Для длительного tail -F события stdout и stderr записываются по мере получения
данных, без ожидания завершения потока. stdout также пишется в logs/tinyproxy.log.
Ошибки stderr появляются в журнале сразу. spawn содержит PID локального процесса
ADB, а завершение потока — его код выхода. При штатной остановке процесса чтения
логов поток ADB закрывается и результат записывается в журнал. При принудительном
SIGKILL последнего события finish может не быть; остаются start и уже полученный
вывод.

При SSH fix_interfaces_via_ssh.sh выполняется с bash -x: в stderr видны шаги настройки сети и
запускаемые им команды. Ошибка изменения LogFile/Syslog завершает команду с
ненулевым кодом, без финального ложного logfile-ok.

Посмотреть журнал в реальном времени:

```bash
tail -f logs/adb.log
```

Журнал дописывается несколькими процессами, без автоматической ротации. Его
можно удалить штатным clean_temp.sh вместе с другими логами. При ADB сетевой скрипт не передаётся и не выполняется.


### Переключение режима полёта через ADB

Парсер и scripts/airplane_mode.py используют root-команды
su -c 'cmd connectivity airplane-mode enable' и
su -c 'cmd connectivity airplane-mode disable'. Прямой am broadcast
AIRPLANE_MODE от ADB shell не вызывается: Android запрещает отправку этого
защищённого broadcast пользователю shell (UID 2000).
Код выхода каждой команды переключения проверяется и журналируется.
Если включение не удалось, попытка не признаётся успешной; если выключение
не удалось, tinyproxy не перезапускается в рамках этой попытки.
После успешного включения выключение вызывается в finally при обычном
прерывании ожидания. Принудительное завершение процесса через SIGKILL или
недоступность устройства может помешать выполнению выключения.
